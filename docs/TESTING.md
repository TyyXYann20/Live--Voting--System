# Deployment acceptance checks

Run against a dedicated Supabase test project and production-like HTTPS build. Never load-test a live event session.

| Area                      | Procedure and required outcome                                                                                                                                                                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth                      | Admin password login succeeds; wrong credentials fail. A normal and anonymous user cannot open admin routes or call any admin RPC. Revoking a profile role also rejects RPCs even in an already-open admin tab.                                                 |
| Database grants           | Use a participant JWT to select participants/votes/snapshots: no rows. Try direct insert/update/delete: denied. Try writing `profiles.role`: denied.                                                                                                            |
| Sessions/teams            | Create/edit drafts, add/edit/delete unreferenced teams, start with fewer than two teams (reject), start correctly, edit teams after start (reject), pause/resume, stop, archive.                                                                                |
| Secure registration       | Register a name/team, retain one-time code, verify it on a fresh phone, inspect stored hash, vote once. Invalid code and mismatched registered team fail. After success, replay code on a second device fails.                                                  |
| Atomic rollback           | Own-team or invalid-target attempt fails without binding a code or leaving an open-mode participant row. The same user can then cast a valid vote.                                                                                                              |
| Parallel duplicates       | With the same participant JWT/code, issue 20 `submit_vote` RPC calls using `Promise.allSettled`. Exactly one succeeds, one ballot exists, and the receipt is unique. Repeat from two identities using one unused code.                                          |
| Parallel different voters | Issue valid submissions with at least 50 distinct identities and registered codes concurrently; compare final count with successful calls. Check lock timeouts and event traffic against project limits.                                                        |
| Stop race                 | Race valid votes with admin `session_action(stop)`. Accepted transactions before the stop lock are in the snapshot; all later attempts fail. Vote count and saved snapshot match.                                                                               |
| Schedule                  | Before `start_time` and at/after `end_time`, LIVE session submissions fail. Times do not auto-start/stop.                                                                                                                                                       |
| Visibility                | With fresh unauthenticated/participant clients, `get_results` contains no teams/counts while hidden, result_signals SELECT returns no rows, and no private tables publish. Reveal permits aggregates only. Stop hides again; archive removes public visibility. |
| Realtime                  | Open two projectors, cast votes, and verify counts change without reload and QR remains visible. Watch WebSocket subscriptions and confirm no names, code hashes, participant IDs, or ballots are sent publicly.                                                |
| Recovery                  | Disconnect network, reconnect, and verify status/reconciliation without reload. Block WebSockets while allowing HTTP: counts converge via ten-second polling. A network error shows an error and later recovers.                                                |
| QR                        | Download PNG and scan with iOS/Android. Link has correct HTTPS origin and session ID. Test copy, enlarged QR, print, and fullscreen on the real projector.                                                                                                      |
| Results                   | Validate counts, percentages, ties `1,1,3`, more than three tied podium teams, zero votes, team modal, historical snapshot, and manual winner/back controls. Never announce automatically on stop.                                                              |
| Devices                   | Test 390px phone, 768px tablet, laptop and 1920×1080 projector. Keyboard-only controls, dialog focus/Escape, screen-reader labels, and reduced motion remain usable.                                                                                            |
| Deployment                | Hard refresh every route, verify no console/app errors, run build, confirm no `.env` or service key in Git/build, verify Vercel plan eligibility, CAPTCHA, Supabase capacity and backups.                                                                       |

## Participant management upgrade acceptance

Apply `202610270001_participant_management.sql` once to an existing test project after the original migration. Existing sessions, participants and votes must remain unchanged by applying it.

For fullscreen projector changes (no new SQL): sign in as admin, hide results, and click **Show results & full screen**. Verify that this authorized action reveals the real event's results publicly, all team counts/percentages update with incoming votes, and the QR stays visible on the actual projector. Exit using the button and Escape; fullscreen labels must stay accurate. A fresh public viewer must remain unable to reveal a hidden event. Confirm backend errors keep results hidden and unsupported browsers retain the normal projector view.

- In a live session, revoke a participant's vote. The ballot must disappear from `votes`, live totals must decrease, the original ballot/actor/time must appear only in the admin `participant_events` audit, and the registration must remain.
- Refresh the participant page in the original browser. Submit again with the original team (and original code in secure mode); exactly one replacement vote is accepted. The next duplicate fails. Repeat in both code and open modes.
- Race revoke against a replacement vote on distinct database connections. Session/participant locks must serialize the operations without allowing two active ballots.
- Delete an unused registration and verify its code no longer resolves. A registration with a vote must reject deletion until its vote is revoked. Wrong-session participant IDs, non-admin callers, and direct writes must fail.
- Stop/archive the session and verify revoke/delete/register all reject server-side while the final snapshot remains unchanged.
- Open registration, revoke and delete dialogs at 320px and 390px widths. Confirm centered placement, readable content, touch controls, no page overflow, Tab/Shift+Tab containment, Escape/Cancel behavior, and visible inline server errors. During a pending request, close/cancel/confirm controls must not allow duplicate actions.
- In an open session, verify the page explains automatic registration. For secure sessions, verify manual registration and the one-time code dialog still work.
- Never publish `participant_events`, `votes`, or `participants` through Realtime. Inspect a public subscriber while revoking: visible aggregate results may update, but ballot details and audit records must not leak.

Local automated scope: embedded PostgreSQL tests validate SQL invariants and RLS with real SQL roles, but run within a single embedded instance and do not certify parallel network transactions or Supabase logical replication. Browser tests use HTTP fixtures and intentionally do not claim hosted backend verification. A physically scanned QR, real Auth/CAPTCHA, production Realtime and Vercel deployment require the operator's configuration and devices.
